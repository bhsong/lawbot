# 캘린더 재수집 후 대체된 조문 정리 검증

2026-11-17 KST. 개발 트리와 합성 임시 DB로 [구현 계획](../archives/calendar-superseded-changes.md)의 규칙을 검증했다.

- Red에서 라벨이 바뀐 옛 조문이 `pending`으로 남고 거절·철회 이벤트의 옛 보류가 정리되지 않는 것을 확인했다. 새 CLI 명령이 없어 관련 검증도 실패했다. 같은 라벨 재수집은 기존대로 통과했다.
- 구현 후 재수집에서 옛 행의 상태·검증 시각·보류와 이벤트당 감사 기록을 확인했다. 새 라벨의 자동 승인, 이후 규칙 변경 재수집, 옛 라벨 재등장 시 재판정, 거절·철회 이벤트의 상태 유지를 확인했다.
- `supersede-stale` 미리보기 전후와 두 번째 적용 전후의 DB 바이트가 같았다. 첫 적용은 옛 조문 두 개를 감사 한 줄로 기록했다. 승인 이벤트와 현재 조문은 적용 후 동일했다. `holds-check`는 각각의 이상 건수에 종료 코드 1을, 둘 다 0일 때 종료 코드 0을 반환했다. 실제 캘린더 HTTP 프로세스의 관리자 보류 목록 응답은 정리 전후 동일했다.

| 검증 | 결과 |
| --- | --- |
| 기본 pytest (`.venv/bin/pytest -q`) | 2,086개 통과, 선택 제외 13개, 실패·skip 0개 |
| 단위·계약 | 통과. 재수집·CLI와 가짜 모델 계약 포함 |
| 통합 | 10개 통과. 캘린더 보류 목록 회귀 포함 |
| 대역 E2E | 56개 통과 |
| Ruff·Pyright·스키마·컴파일 | 린트, 포맷, Pyright, 캘린더 API 스키마 및 Python 문법 검사 통과 |
| 프런트엔드 | 챗봇·캘린더 타입 검사, Vitest 각각 55개·31개, 양쪽 빌드 통과 |
| 실제 모델 E2E·모델 스모크·품질 평가 | 실행 안 함. 실제 모델 호출 0회 |

첫 전체 실행에서 `python -m pytest`가 요청 로그의 `caller`를 다르게 기록해 챗봇 계약 테스트 1개가 실패했다. CI와 같은 `pytest` 실행 파일로 해당 테스트를 확인한 뒤 전체를 다시 실행해 통과했다.
