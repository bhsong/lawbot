        │ erp-updates collect                         │ erp-updates attach
        ▼                                             ▼

        │ erp-updates review approve / reject

## 날짜 규칙

- 고시: 머리말 `시행일자`를 적용 시작일로 쓴다. 달력 날짜(이달의 자료)에 올린다.
- 별표·서식과 조문: 저장소 사본은 지금 시행 중인 법령본이다. 그 서식·조문의 시행일은 알 수 없다. 법령 머리말의 `시행일자`를 "현행 법령본 기준일"로만 표시하고 달력 날짜에는 올리지 않는다.
- 게시일·공포(발령)일·시행일을 다른 필드와 라벨로 나눈다. 모두 KST 날짜다.

## PR 나누기

### PR 1 `feat/erp-updates-core`: 수집·검토·피드 (화면 없음)

- `services/erp-updates`: 패키지 `erp_updates`, Python 3.14, 독립 uv 프로젝트(자체 `uv.lock`), 루트 workspace `exclude`. 의존성은 PyYAML뿐이다. 네트워크 코드는 없다.
- `collect --repos <monitor 저장소 폴더>`: `git --git-dir … ls-tree/show`로 HEAD를 읽는다. monitor 잠금은 잡지 않고, 쓰지 않는다.
  - 항목 ID는 키 + 원천 식별자(행정규칙ID, 별표 구분·번호, 파일 경로 + 조문)에서 만든다.
  - 버전 키는 내용 SHA-256이다. 고시는 파일 전체, 조문은 조문 블록, 별표·서식은 제목·구분·번호다. flSeq 링크는 개정 때마다 바뀌므로 버전 키에서 뺀다.
  - 같은 내용을 다시 읽으면 새 버전은 0건이고 수집 이력에 "변경 없음"으로 남는다.
- `attach --file <PDF> --url <원천 링크>`: 링크가 최신 버전의 원천 첨부 목록에 있어야 하고, 파일 앞부분이 `%PDF`여야 한다. 복사본과 SHA-256·크기를 기록한다.
- `list`, `review approve|reject <id> --reviewer <이름> [--reason]`: 새 버전은 `pending`이다. 이전 승인은 이력으로 남는다.
- `export --out <파일>`: 최신 버전이 승인된 항목만 넣는다. 본문은 상한 4,000자다. 내부 경로·검토자 이름은 넣지 않는다. 임시 파일에 쓴 뒤 `os.replace`로 바꾼다.
- 공개 피드 v1에 넣는 것:
  - 항목: 키, 제목, 분류, 원천 종류, 고시명·발령번호·발령일·시행일 또는 법령명·조문·현행 법령본 기준일, 본문 발췌, 공식 출처 링크, 첨부(제목·공식 PDF 링크·SHA-256·바이트), 내용 SHA-256, 승인 시각
  - 관련 법령명 목록: 설정의 별표·서식·조문 원천에서 나온다
  - 수집 이력: 공개 항목마다 가져온 시각, 원천(저장소 커밋 또는 등록한 파일), 결과(새 버전, 변경 없음, 파일 등록), 승인 시각
- CI: `uv pip install --no-deps -e services/erp-updates`, pyright, 피드 스키마 검사. pytest `testpaths`에 테스트 폴더를 추가한다.

### PR 2 `feat/law-calendar-erp-tab`: API와 화면

- law-calendar `--erp-feed` 옵션과 환경 변수 `LAW_CALENDAR_ERP_FEED`(선택). `GET /api/erp-updates`는 상태(`ok`·`missing`·`invalid`)와 피드를 돌려준다.
  - Pydantic으로 검증하고, 검증에 실패하면 `invalid`에 항목 0건으로 응답한다.
  - 기존 API와 TypeScript 생성 계약은 그대로 두고 새 모델만 추가한다.
- 화면: 머리말 아래 탭 `법령 캘린더` / `ERP 자료`(`#erp`로 바로 연다). ERP 코드는 `frontend/src/erp/`에만 둔다.
  - **현재 적용 중**: 적용 시작일이 오늘(KST) 이전인 승인 항목과 현행본 기준 항목
  - **예정**: 적용 시작일이 오늘 이후인 항목
  - **이달의 관련 법령 일정**: `/api/law-events?month=`에서 관련 법령명만 걸러 보여 주고, 기존 상세 대화상자로 연다
  - 항목 카드: 본문 발췌, 날짜 라벨, 공식 링크, 첨부 PDF 링크와 SHA-256
  - **수집 이력** 버튼: 대화상자에 표(항목, 원천, 가져온 시각, 결과, 승인 시각)를 보여 준다
- 피드가 없거나 손상돼도 법령 캘린더 탭은 그대로 동작한다. ERP 탭에는 안내만 보이고 가짜 자료는 넣지 않는다.

### 나중 (별도 요청)

- monitor `lawgo_forms`·`lawgo_admrul` 이벤트 읽기: 개정된 별표·서식의 PDF(`data/files`)와 서식별 시행일을 자동 등록하고, 버전을 텍스트 SHA-256으로 비교한다. 지금은 이벤트가 0건이라 시연에는 필요 없다.
- 간이세액표·산재 업종별 전체 표 파싱. 그 전에는 "원문 PDF 참고"로만 표시한다.

## 완료 기준

PR 1:

1. 합성 bare 저장소 두 개(실제 레이아웃과 같은 머리말)에서 6개 키를 수집한다. 다시 수집하면 새 버전 0건이다.
2. 원천 내용이 바뀌면 새 버전이 `pending`으로 생기고, 승인 전에는 피드에서 그 항목이 빠진다.
3. flSeq만 바뀐 경우에는 새 버전이 생기지 않는다.
4. 승인하지 않은 항목은 피드에 없다. 피드에 로컬 경로·검토자·토큰 형태 문자열이 없다.
5. `attach`는 원천 목록에 없는 링크와 PDF가 아닌 파일을 거부한다.
6. 실행 전후로 저장소 사본의 파일 해시가 같다.
7. 날짜 미확정 항목(별표·서식·조문)에는 달력 날짜가 없다.

PR 2:

1. API: 피드가 정상, 없음, 손상일 때 각각 응답하고, 기존 API 응답은 바뀌지 않는다.
2. Vitest: 탭 전환, 현재·예정 분류, 관련 법령 걸러내기, 수집 이력 대화상자.
3. 대역 E2E(`e2e_stub`, 운영 빌드 + 합성 DB·피드): 처음부터 ERP 탭을 열고, 카드와 SHA-256, 관련 법령 일정, 수집 이력 표를 확인한다. 피드가 없을 때도 법령 캘린더 탭이 정상인지 확인한다.

두 PR 모두 전체 Green(루트 pytest, ruff, pyright, 두 서비스 잠금·스키마 검사, 캘린더 화면 typecheck·test·build)을 통과한 뒤에 PR을 연다. 실제 모델 호출은 없다.

## 시연 준비 (병합 뒤, 별도 승인)

운영 monitor 저장소 사본을 읽어 `collect`를 실행하고, PDF 3건을 `attach`한다. 사용자가 승인한 뒤 `export`한다. 이어서 운영 캘린더에 `LAW_CALENDAR_ERP_FEED`를 설정하고 재시작한다. 운영 데이터와 서비스를 바꾸는 단계라서 diff, 명령, 대상을 보여 주고 승인을 받는다. 결과는 `docs/evals/`에 기록한다.
