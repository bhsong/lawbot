# 계획: 조문 CSV 생성기

- 작성일: 2026-11-02
- 목표: Legalize KR 원문과 기준일만으로 `data/v4/articles_v4.csv`(법률 423행)와 `data/v4/law_articles_v4_decree.csv`(법률 + 시행령·시행규칙 840행)를 **바이트 단위로 똑같이** 다시 만든다. 다음 차례인 monitor 연결·`lawbot-reindex`가 이 생성기의 출력을 받는다.
- 출발점: 사용자가 준 하위법령 스크립트(`build_decree_articles`). 하위법령 840행은 이미 바이트 단위로 일치한다(legalize-kr `8c89174` 기준). 이 스크립트는 법률 행을 입력 CSV에서 그대로 복사한다.

## 1. 미리 확인한 사실

- 법률 본문을 머리말 `시행일자` ≤ 기준일인 최신 버전 하나에서 뽑으면 비삭제 415조문 중 399개가 일치한다. 불일치 16개는 모두 근로기준법이다.
  - 15개(제13조, 제43조의6, 제54조, 제60조, 제61조, 제101~105조, 제102조의2, 제108조, 제110조, 제114조, 제116조): 이 버전에 들어 있지만 부칙상 시행일이 기준일 뒤인 개정이다.
  - 1개(제53조): 원문에 없는 `[실효: 2022.12.31.까지 유효]`를 손으로 붙였다 (`docs/data-provenance.md` 2절).
- 파일에는 지금까지의 부칙이 모두 쌓여 있다. 버전마다 자기 부칙은 `<제{공포번호}호,…>` 머리로 찾는다. 시행일은 부칙 제1조 형식이 일정하다: "이 법은 ○부터 시행한다. 다만, ○의 개정규정은 ○부터 시행하고, …". 날짜 표현은 `공포한 날`, `공포 후 N개월(년)이 경과한 날`, `YYYY년 M월 D일`이다.
- 부칙 예외에는 장 제목도 나온다 (제21533호 "제11장의 제목").
- `related_ids` 재현: 414/415. 다른 1건(임금채권보장법 제10조)은 본문의 "근로자퇴직급여보장법 **부칙 제2조**제1항"을 같은 법 제2조로 잘못 읽은 것이다. **지금 CSV가 맞다.** 생성 규칙에서 '부칙 제N조'를 참조에서 빼야 한다.
- 줄바꿈: `articles_v4.csv`는 행 끝이 CRLF이고 decree CSV는 LF다. 둘 다 UTF-8 BOM이다.

## 2. 설계

위치는 `tools/lawbot-tools/src/lawbot_tools/build_articles.py`이고 명령은 `lawbot-build-articles`다. 런타임은 import하지 않는다 (`test_layers`).

```
uv run lawbot-build-articles --repo ../legalize-kr --asof 2026-10-20 --out-dir data/v4 [--check]
```

- **법률 행: 조문별 시행일 조합.** 파일 이력(커밋 날짜 = 공포일)에서 공포일 ≤ 기준일인 버전을 오래된 것부터 차례로 본다. 직전 버전과 비교해 바뀐 조문(신설·삭제 포함)마다 그 개정의 시행일을 정한다. 기본값은 머리말 `시행일자`이고, 부칙 제1조 '다만'에 조문이 있으면 그 날짜를 쓴다. 시행일이 기준일 이하인 변경만 반영한다. 장 제목(chapter)도 같은 규칙을 따른다. 조문 일부(호)만 예외로 적힌 경우에는 그 조문에 적힌 날짜 중 가장 늦은 날을 쓴다.
- 나머지 열(제목, 장, 삭제, `effective_date`, `related_ids`)은 지금 스크립트의 규칙을 쓴다. 법률 삭제 조문의 비어 있는 제목·본문은 지금 CSV 형식에 맞춘다.
- **보정 목록**: `tools/lawbot-tools/src/lawbot_tools/article_overrides.json`. 원문에 없는 수작업 가공을 `{article_id, field, find, replace, reason}`으로 적는다 (지금은 제53조 두 군데). 보정이 원문에 적용되지 않으면(`find` 없음) 생성을 실패시켜, 원문이 바뀐 걸 모른 채 넘어가지 않게 한다.
- **하위법령 행**: 사용자 스크립트를 그대로 옮긴다. 입력 CSV 대신 위에서 만든 법률 행을 받는다.
- **출력**: 두 CSV와 `versions.csv`(문서별 쓴 버전)를 쓴다. `--check`는 쓰지 않고 기존 파일과 바이트 비교만 해서, 다르면 첫 차이를 보여 주고 종료 코드 1로 끝낸다. 실행할 때 받은 저장소 HEAD 커밋을 출력에 적는다. 그 커밋까지의 이력에서 기준일로 고르는 방식이라, 커밋과 기준일이 같으면 결과도 같다.

## 3. 순서 (커밋)

1. 이 계획.
2. 생성기와 테스트. **기존 두 CSV와 바이트 단위로 일치**하는 상태다. `related_ids` 규칙은 기존 CSV를 재현하는 그대로 둔다.
3. '부칙 제N조' 참조 제외 규칙을 고친다. 고쳐서 하위법령 행의 `related_ids`·`parent_ids`가 바뀌면, 바뀐 조문을 하나씩 원문과 대조해 이 계획 아래에 적고 사용자에게 보고한다(데이터 변경은 확인받은 뒤). 바뀌지 않으면 커밋만 남긴다.
4. 문서: `docs/data-provenance.md`의 "바꾸는 방법"을 생성기 명령으로, `docs/operations.md`에 사용법 한 줄.

## 4. 테스트

- 단위 테스트(기본 실행): 부칙 시행일 해석(공포한 날·N개월·N년·날짜, '다만' 여러 개, 장 제목, `부터 … 까지` 범위), 작은 git 저장소를 임시로 만들어 조문별 시행일 조합(시행 전 조문은 이전 본문, 신설은 빠짐, 삭제 반영), 보정 적용과 `find` 없음 실패, '부칙 제N조' 규칙(커밋 3), CSV 줄바꿈(CRLF·LF).
- 합격 테스트(`-m network`, 기본 제외): legalize-kr을 받아 기준일 2026-10-20으로 만들고, 두 CSV가 레포 파일과 바이트 단위로 같은지 본다. 레포 위치는 `LEGALIZE_KR` 환경 변수로 넘긴다.
