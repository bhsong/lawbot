# 국회 입법예고 PDF 자동 다운로드와 대비표 미리보기 제거

- 작성일 2026-11-13 KST. 개발 기준 `main` `58707fec0d742a5eefa2207cb3c487aca071a9b2`.
- 별도 수정 PR에서 구현한다. 운영 적용과 데이터 정리는 구현 및 사본 검증 뒤 대상과 명령을 확인해 승인받는다.
- 개발 브랜치 `fix/remove-assembly-pdf-preview`에서 구현했다. 운영 반영과 운영 원본 DB 정리는 승인 대기다.

## 목표와 화면 동작

- 입법예고 일정을 클릭하면 기존 상세 다이얼로그를 연다. 주요 변경 내용, 예고 기간, ‘공식 원문 확인’ 링크를 표시한다.
- 공식 상세에서 PDF URL이 확인된 경우 ‘법률안 PDF 원문 (새 창)’ 링크를 제공한다. 사용자가 링크를 눌러 국회 사이트에서 직접 열 수 있다. PDF 주소가 없으면 공식 상세 링크를 제공한다.
- 국회 입법예고 PDF 자동 다운로드, 페이지 이미지 생성·저장·재시도, ‘공식 신·구조문대비표’ 펼침 영역을 제거한다. 공개 캘린더와 인증 관리자 화면에서 이미지 API도 제거한다.

## 구현 순서

1. 기존 국회 입법예고 fixture로 목록과 상세, 의안번호·예고기간 대조, 자동 공개, 주요 변경 내용, 공식 상세·PDF 링크를 고정한다. 정기 sync와 수동 `notice-content`에서 PDF 요청이 0건이어야 하는 시험을 먼저 작성한다. 캘린더와 관리자 화면의 다이얼로그 및 링크를 대역으로 검증한다.
2. 캘린더가 공식 상세 HTML에서 주요 내용과 검증된 PDF 링크를 저장하도록 유지한다. PDF 다운로드와 렌더러 호출, 첨부 재시도, 처리 한도 상태 및 관련 로그·CLI 출력을 정리한다. 의안번호·예고기간 대조와 승인 이력은 유지한다. PDF 처리에만 쓰는 의존성은 저장소 전체 사용처를 확인한 뒤 제거한다.
3. 공개 `GET /api/law-changes/{change_id}/notice-comparison/{page}`, 인증 관리자 프록시의 이미지 경로, 상세 응답의 `comparisonPages`·`comparisonLimited`와 대응 TypeScript 계약을 제거한다. 공유 다이얼로그와 두 앱에서 이미지 표시를 정리하고 공식 링크를 유지한다. 일반 시행 일정의 저장 조문 비교, 챗봇 대화·검색·조문 자동 갱신 계약을 회귀 검증한다.
4. 명시적으로 실행하는 캘린더 DB 마이그레이션을 추가한다. `assembly_notice_pages`를 제거해 저장된 대비표 이미지를 전부 정리하고, PDF 재시도·처리 한도 전용 상태를 정리한다. 기존 일정, 공지 본문과 `pdf_url`, 승인·시도 이력을 보존한다. 빈 DB 초기화, 이전 버전 업그레이드, 반복 실행과 실패 시 트랜잭션 복구를 사본에서 확인한다.
5. 법제처 Open API와 별표·서식 첨부의 최초 요청 및 리다이렉트를 법제처 공식 HTTPS 호스트로 제한한다. 차단된 목적지는 요청하지 않고, 공식 상대 경로와 같은 호스트의 정상 리다이렉트를 대역으로 검증한다. 챗봇 조문 갱신의 Git 입력과 실행 경로는 그대로 유지한다.

## 검증과 운영 정리

- 이미지 API 요청은 공개·관리자 양쪽에서 404를 반환한다. 상세 다이얼로그는 공식 상세 링크를 표시하고, 확인된 PDF 주소가 있으면 새 창 링크를 표시한다. 두 링크는 화면을 여는 것만으로 PDF 요청을 보내지 않는다.
- 정기 sync 및 수동 갱신의 PDF 요청은 0건이다. 사본 마이그레이션 전 이미지 행 수와 마이그레이션 후 이미지 테이블 제거를 확인한다. `PRAGMA quick_check`와 `PRAGMA foreign_key_check`를 실행하고, 보존 대상의 건수와 내용을 비교한다. 기본 pytest, 두 화면의 타입·테스트·빌드, Ruff·Pyright·스키마·잠금 파일 검사를 실행한다.
- 승인 후 등록된 운영 캘린더 DB와 배포 대상 커밋을 확인한다. 배포 창에서 DB 쓰기를 조정하고 일관된 사본을 백업해 검증한다. 백업은 접근 제한과 보존 기한을 정한다. 운영 DB 정리 시 WAL과 삭제 페이지의 이미지 잔존 여부를 확인하고, 필요한 경우 검증된 SQLite 정리 절차를 적용한다.
- 변경 diff를 기준으로 두 화면 빌드와 필요한 서비스 재시작 범위를 정한다. 운영에서 일정과 상세 링크, 이미지 API 404, 이미지 테이블 제거, 다음 수집의 PDF 요청 0건을 확인한다. 정리 완료된 운영 DB로 이미지 없는 새 백업을 만들고 무결성·외래 키·보존 데이터 일치를 검증한 뒤, 이미지가 남은 복구용 백업의 경로와 삭제 명령을 확인해 제거한다. 정리 실패 시 새 쓰기를 멈추고 기존 백업으로 복구 가능 여부를 확인한다.
