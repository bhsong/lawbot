# 캘린더 재수집 후 남는 숨은 보류 조문 정리

## 문제

2026-11-17 운영 캘린더 DB(읽기 전용)에서 `pending` 조문 20개를 찾았다. 화면 어디에도 나오지 않았다.

- 소속 이벤트 8개는 모두 승인 상태이고, 공개 조문 34개가 이미 나가 있다.
- 20개는 모두 예전 파서(monitor-law-v1·v5)로 만든 수집본에 묶여 있다. 같은 원문을 v6 파서로 다시 가져오면서 조문 라벨이 항 단위로 바뀌었다. 예: `제110조` → `제110조 제1호`.
- 새 라벨 행은 자동 승인됐고, 옛 라벨 행은 `pending`과 옛 수집본의 보류로 남았다.
- 관리자 보류 목록(`public_holds`)은 이벤트의 현재 수집본에 있는 조문만 보여 준다. 그래서 20개가 공개 캘린더에도, 관리자 화면에도 나오지 않았다.

원인은 `ingest.import_event`이다. 새 수집본을 가져올 때 이벤트의 모든 조문을 `pending`으로 되돌린다. 그런데 새 수집본에 없는 조문은 다시 판정하지 않고 그대로 남긴다.

## 목표

- 새 수집본에 없는 조문이 `pending`으로 남지 않는다.
- 이미 남아 있는 행도 같은 규칙으로 정리된다.
- 숨은 보류가 다시 생기면 매일 점검에서 바로 보인다.

## 규칙 (모든 이벤트에 하나만 적용)

이벤트의 현재 수집본(`event_sources.snapshot_id`)에 `change_versions`가 없는 조문은 **대체된 조문**이다.

1. 가져오기에서 대체된 조문은 `withdrawn`으로 바꾸고 `verified_at`을 비운다. 보류 행(`held_changes`)도 지운다.
2. 감사 기록(`review_audit`)에 이벤트당 한 줄을 남긴다. decision은 `withdraw`, reviewer는 `import-adapter`, note는 `Superseded by snapshot <id>`이다. 상세(`review_details`)에는 대체된 조문 id 목록을 넣는다.
3. 이벤트 자체의 상태와 현재 수집본의 조문은 건드리지 않는다.
4. 거절이나 철회와 달리 내용 판단이 아니다. 같은 원문이 다시 바뀌어 그 라벨이 돌아오면 새 행으로 다시 판정한다. 같은 id면 기존 upsert가 `pending`으로 되돌린다.

## 변경

1. `ingest.import_event`: 새 수집본의 `changes`를 기록한 뒤, 그 이벤트에서 현재 수집본 밖에 있는 조문에 위 규칙 1·2를 적용한다.
2. 기존 데이터 정리: `manage.py`에 `supersede-stale` 명령을 추가한다. 기본은 미리보기(대상 조문 목록만 출력)이고, `--apply`를 주면 같은 규칙을 한 트랜잭션으로 적용한다. 여러 번 실행해도 결과가 같다.
3. 점검: `manage.py`에 `holds-check` 명령을 추가한다. 다음 두 수를 출력하고, 0이 아니면 종료 코드 1로 끝난다.
   - 현재 수집본 밖에 있는 `pending` 조문 수
   - `held_changes`에 있지만 `public_holds`에 나오지 않는 `pending` 조문 수
   - 매일 06:41 점검 항목에 이 명령을 넣는다(`docs/operations.md`).
4. 관리자 보류 목록과 `public_holds` 뷰는 바꾸지 않는다. 대체된 조문은 사람이 검토할 대상이 아니다. 자동화 후 점검 방침에 따라 점검 명령으로만 드러낸다.

## 테스트 (TDD)

- 단위: 라벨이 `제110조`인 수집본을 가져온 뒤, 같은 이벤트를 `제110조 제1호` 라벨로 다시 가져온다. 옛 행은 `withdrawn`이 되고, 보류 행이 없고, 감사 한 줄이 남는다. 새 행은 자동 판정된다.
- 단위: 새 수집본에 같은 라벨이 있으면 그 행은 대체로 처리하지 않는다(기존 동작 유지).
- 단위: 승인된 이벤트를 다시 가져와도 현재 수집본 조문과 이벤트 상태는 바뀌지 않는다.
- 단위: `supersede-stale` 미리보기는 DB를 바꾸지 않는다. `--apply`는 두 번 실행해도 결과가 같다.
- 단위: `holds-check`는 숨은 보류가 있으면 1, 없으면 0으로 끝난다.
- 통합: 관리자 보류 목록 API의 결과는 바뀌지 않는다.
- 기본 테스트 전체와 린트를 실행한다. 실제 모델은 쓰지 않는다.

## 운영 반영

- 반영 후 `holds-check`가 0·0인지 확인한다. 다음 06:30 수집 뒤 점검에서도 확인한다.
