1. 프로젝트 컨텍스트 및 목표 (Context & Objective)

1.1 원문에서 제시한 환경

원문은 services/model-server가 임베딩(emb_v5)·Cross-Encoder 리랭커·MLX 생성 모델을 서빙하고, services/chatbot이 SQLite·RAG·어드민을 담당하는 모노레포라고 설명한다. 이 문서는 그 구조를 구현 탐색의 출발점으로 삼는다.

원문의 검색·리랭킹 3초 이내, 생성 15~30초는 제공된 설명값이다. 이번 개정에서 장비·부하·시작/완료 정의를 고정해 재측정하지 않았다. 현재 레포·패키지·모델 파일과 CONTEXT.md도 확보하지 못했다. 따라서 경로와 모델 이름은 실제 레포에서 확인할 대상이다.

사용자 설명에 따라 매 질문은 대화 이력 없이 처리한다. 다만 “그럼 얼마인가요?”처럼 단독으로 해석할 수 없는 질문을 맥락 독립 질문으로 간주하지 않는다.

1.2 목표와 제외 범위

• 승인된 동일 질문은 exact 경로에서 임베딩·리랭커·생성 LLM 없이 반환한다.
• 표현이 달라도 승인된 재사용 범위와 조건이 맞는 경우에만 semantic 경로에서 생성 LLM을 생략한다.
• 두 캐시가 미스여도 기존 RAG 검색 범위를 보존하고 원자 검색 결과로 보완한다.
• 새 생성 답변은 관리자가 검수할 pending 후보로만 제출한다. 승인 전 공용 캐시 반환은 금지한다.
• 같은 답변·근거·승인·배포를 두 저장소가 별도로 관리하지 않는다.

이번 기능만으로 모든 법률적 조건을 자동 해석하거나 오류를 완전히 제거한다는 주장을 하지 않는다. 캐시 불통과는 사용자 질문 거절이 아니라 기존 RAG로의 전달이다. RAG도 근거나 사실관계가 부족하면 기존 확인 요청·판단 유보 정책을 따른다.

시맨틱 재사용의 초기 허용 의도는 제한한다. 질문 생성 범위와 실제 반환 가능 범위는 서로 다를 수 있다. 초기 원자 구축 범위는 §10의 확인 사항으로 남긴다.

3. 데이터베이스·원자 인덱스·어드민 승인 (SQLite & Vector Index)

3.1 원본 조문 참조와 전체 근거

기존 조문 ID 또는 chunk ID를 부모로 사용한다. 법령명 없이 제9조만으로 식별하지 않는다.

parent_chunk_id는 원자에서 원문으로 돌아가는 검색 연결이다. 답변 전체의 근거 목록을 대신하지 않는다. 아래를 별도로 보존한다.

• 표시 근거: display_citation_article_ids, display_citation_hashes
• 무효화에 필요한 의존 근거: dependency_article_ids, 각 원문 hash
• 생성 시 제공한 컨텍스트: generation_context_ids, 각 원문 hash
• corpus_snapshot_id, answer_policy_version, answer_revision_id
• atom_revision_id, reuse_policy_version, active_release_id

생성에 제공한 모든 조문이나 검토자가 읽은 모든 조문을 표시 근거로 자동 전환하지 않는다. 필요한 근거가 없거나 해시가 맞지 않으면 답변만 반환하지 않는다. 답변 본문은 옛 버전인데 패널 조문만 최신으로 교체하는 동작을 금지한다.

아래는 책임 분리 명세다. 기존 테이블이 역할을 수행하면 재사용한다. migration 이름 0003_...는 실제 번호를 확인하기 전 확정하지 않는다.

새 테이블에 candidate_answer와 cached_answer를 승인 상태와 함께 이중 저장하는 방식은 피한다. 기존 스토어의 후보·답변 revision을 참조하고, 원문의 해당 필드는 어드민 응답 어댑터에서 보여줄 수 있다.

같은 답변이 여러 원자에 연결되는 것은 허용하되, 각 연결의 재사용 범위는 따로 검수한다. 다대다 저장을 지원한다는 이유로 여러 원자의 답변을 온라인에서 합성하는 기능을 추가하지 않는다. 초기 자동 반환은 승인된 단일 의도·완성 답변 하나로 제한한다.

3.3 질문 조건 검사

기존 답변 채점용 must_include와 사용자 질문의 재사용 조건을 혼용하지 않는다.

|`query_must_include`          |그룹 간 AND, 그룹 안 OR인 필수 표현         |
|`query_must_not_include`      |하나라도 발견되면 해당 정책 재사용 차단           |

|`allowed_optional_slots`      |추가돼도 답변이 달라지지 않는다고 검수한 조건        |
|`unsupported_condition_policy`|초기 고정값 `bypass`                  |
|`supported_query_patterns`    |해당 정책이 지원하는 문장/의도 범위와 반례         |
|`reuse_policy_id/version`     |변경 불가능한 정책 리비전                   |

조건 결과에는 질문의 근거 구간과 known / missing / ambiguous / unsupported를 남긴다.

• 필수 조건 누락·충돌, 미지원 추가 조건, 불명확한 부정, 승인되지 않은 복합 의도는 캐시 미스로 처리한다.
• 5인 이상과 5인 미만 같은 비교 표현은 다른 조건이다. 이 예시는 문자열 비교 반례이며 법률 적용 판단을 뜻하지 않는다.
• 직원 4명 같은 표현을 자동으로 법률상 인원 기준과 동일시하지 않는다. 측정 대상·산정 기준·시점까지 지원 정책에서 검수한 경우만 정규화한다.
• 특정 단어가 존재한다는 사실만으로 조건 충족으로 보지 않는다. 인용·질문형·부정 범위를 확인한다.
• 조건을 찾지 못했다고 “조건 없음”으로 승인하지 않는다. 지원 범위 밖이면 우회한다.
• 일반 설명형 답변이 특정 조건 없이도 재사용 가능할 수는 있다. 그 범위를 정책에 명시하고 검수해야 하며, 단순히 빈 배열이기 때문에 모든 질문을 허용하지 않는다.
• 초기 추출은 의도별 사전·규칙·결정적 파서를 사용한다. 별도 온라인 생성 LLM을 조건 추출 필수 단계로 넣지 않는다.
• 리랭커 점수가 매우 높아도 조건 실패를 뒤집을 수 없다.

원자·후보 수집용 정책은 검수 대상으로 존재할 수 있지만, 그것만으로 답변의 시맨틱 재사용이 승인된 것은 아니다.

3.4 pending 및 수동 승인 정책

원문 정책을 유지한다. 자동 저장은 pending이고, 관리자가 확인한 답변만 승인한다.

여기서 보완하는 것은 승인 횟수가 아니라 무엇을 보고 무엇을 승인하는지다.

관리자는 같은 화면에서 다음을 확인한다.

1. 실제 사용자 질문에 저장 답변이 맞는지.
2. 대표 원자 질문과 명시한 재사용 조건 범위에도 그대로 쓸 수 있는지.
3. 전체 표시 근거·의존 근거·법령 버전이 맞는지.
4. 개인정보·개별 사건·시점 의존 내용이 공용 답변에 남아 있지 않은지.
5. 지금 보고 있는 candidate/answer/policy revision이 실제 승인 대상인지.

한 번의 검수와 승인 동작으로 내용과 시맨틱 허용 범위를 함께 기록할 수 있다. 이를 이유로 내용 승인·시맨틱 승인·운영 승인을 별도의 세 번 클릭으로 강제하지 않는다. 다만 의미 재사용 허용 여부는 데이터상 명시적으로 남긴다.

기존 코드가 승인 → 배포를 나누면 그대로 유지한다. 기존에 승인·배포 결합 액션이 있다면 동일 검증과 트랜잭션을 적용해 재사용한다. 새 pending 자동 등록을 승인이나 배포로 취급하는 것은 어느 경우에도 금지한다.

|상태/사건                                       |런타임 처리                                    |
|--------------------------------------------|------------------------------------------|
|빈 슬롯, `pending`, `hold`, `rejected` 후보      |그 후보 답변 반환 금지                             |
|내용 승인만 있고 시맨틱 범위 미승인                        |시맨틱 반환 금지. exact 허용 여부는 기존 exact 승인 정책에 따름|
|승인됐지만 활성 release에 없음                        |캐시 반환 금지                                  |
|semantic 허용 연결 + 승인 답변 revision + 활성 release|다른 모든 게이트까지 통과하면 반환 가능                    |
|후보 편집                                       |새 revision 생성. 이전 revision을 본 승인으로 덮어쓰기 금지|
|신규 수정 후보가 pending                           |기존 유효 배포본을 자동 덮어쓰지 않음                     |
|배포본 철회·근거 무효화                               |해당 revision 반환 차단. pending 후보로 대체 반환하지 않음 |

이 상태들은 기존 어드민 모델에 매핑하는 논리 계약이다. review_status='approved' 단독으로 반환 가능성을 결정하지 않는다.

3.5 어드민 UI 재사용

CachePanel.tsx, adminApi.ts, 기존 API와 스토어를 우선 재사용한다. 필수 검수 정보가 없으면 작은 필드·상세 패널 확장을 허용한다.

검수 화면은 대표 원자 질문, 실제 인입 질문, 원자 명제, 답변 전체, 변경 diff, 전체 근거, 조건 정책·반례, snapshot, candidate/answer revision, 의미 재사용 허용 여부와 배포 상태를 보여준다.

원문 last_matched_query는 현재 승인본의 의미를 덮어쓰는 최신 문자열이 아니라 후보 생성 기록에 귀속한다. 질의 원문은 관리자 권한·보존 정책에 따라 저장·표시한다.

기존 엔드포인트·DTO 호환성을 테스트하고, 새 필드가 필요하면 호환 가능한 확장 또는 명시적인 API 버전을 사용한다.

3.6 원자·질문 구축 Tools

고정한 corpus snapshot
→ 원문 위치·대상·조건·예외를 보존한 원자 추출
→ 원자별 예상 질문 생성
→ 원문-원자-질문 연결 검토
→ 중복·조건 충돌·평가 누수 검사
→ 임베딩 생성
→ 검증 manifest와 함께 인덱스 활성화

원자 수·질문 수는 고정하지 않는다. 원문이 뒷받침하지 않는 조건·정답·대명사 해석을 생성 과정에서 추가하지 않는다. 의미를 유지하는 데 필요한 단서·예외·정의는 원자에 유지하거나 의존 관계로 연결한다.

검색용 원자 질문을 생성했다고 캐시 답변을 자동 생성·승인한 것으로 처리하지 않는다. 기존 통과 답변을 연결할 때도 새 원자 질문과 조건 범위에 적합한지 검수한다.

3.7 벡터 인덱스

SQLite와 기존 인메모리 벡터·프리페치 구조를 우선 재사용한다. 별도 서버형 벡터 DB 도입은 이번 필수 범위가 아니다.

저장 원자 질문과 사용자 질문은 동일한 질문 인코딩 계약을 사용한다. 프로젝트의 prompt_name='query' 규칙과 실제 모델 설정을 확인한다. fingerprint에는 가중치 revision, tokenizer, prompt hash, 전처리·길이, 차원, 정규화, backend·정밀도를 포함한다.

다음에는 불완전한 벡터로 캐시 반환하지 않는다: 입력 잘림, 0 벡터, NaN/Inf, 차원 불일치, manifest 불일치, DB에 없는 query revision, 모델 변경 후 구 벡터 혼용.

인덱스는 불변 generation으로 만들고 검증 후 원자적으로 활성 포인터를 바꾼다. 요청 중 배열을 제자리 수정하지 않는다. worker별 구 버전은 반환 직전 DB/release 검사로 차단한다.

기본 검색 범위는 유효한 snapshot·권한·law scope·검토된 원자 질문이다. 미승인 답변과 연결된 원자도 검색/후보 수집에 쓰일 수 있지만, 검색됨과 반환 가능함은 반드시 분리한다.

4. 런타임 처리 명세 (Runtime Pipeline Specs)

4.1 전체 흐름

입력·권한·scope 검사, 활성 corpus/release 확인
    │
    ├─ 정확 일치 캐시 적중
    │      └─ 승인 답변 revision + 같은 snapshot의 근거 반환
    │         임베딩 0회, 리랭커 0회, 생성 LLM 0회
    │
    └─ 정확 일치 미스
           │
           ├─ semantic=off → 기존 RAG 그대로
           │
           └─ 질문 임베딩 → 원자 질문 검색 → 부모 조문 복원
                  → 질문 조건 검사 + 원자/부모 페어 리랭킹
                  → 승인·배포·근거·경쟁 후보·재사용 조건 검사
                        │
                        ├─ semantic=on이고 모든 게이트 통과
                        │      └─ 승인 캐시 답변 + 근거 반환, 생성 LLM 0회
                        │
                        └─ 시맨틱 미스
                               → 기존 조문 검색을 독립 실행
                               → 기존 후보 ∪ 유효한 원자 부모 후보
                               → 중복 제거 → RAG 리랭킹
                               → 기존 하위법령·보충 근거·컨텍스트 구성
                               → 기존 LLM 스트리밍
                               → 정상 완료 후 조건부 pending 제출

shadow에서는 would-hit만 기록하고 실제 캐시 답변을 반환하지 않는다. 그림의 합집합 경로는 on에서의 정상 미스 동작이다. shadow에서 사용자 응답을 바꾸지 않는 방식은 §4.3을 따른다.

[Step 0] 정확 일치 우선 조회

단일 dispatcher가 최종 응답을 한 번만 선택한다. exact_cache.py를 제거하거나 atomic 모드에서 자동 비활성화하지 않는다.

기존 exact 모드가 켜져 있으면 정상화한 질문·namespace·scope·snapshot·정책으로 조회하고, 승인·active release·기한·철회·전체 근거를 확인한다. 새 의미 인덱스에 없는 exact 항목도 기존 계약이 유효하면 반환할 수 있다.

exact hit는 후속 semantic 조회·임베딩·리랭킹·생성을 모두 종료한다. exact miss는 의미 캐시로 넘어간다. 공통 승인 저장소의 상태를 확인할 수 없는 장애라면 semantic도 우회한다. 장애가 임베딩/리랭커 등 RAG 공통 구성요소까지 영향을 주면 기존 오류 정책을 따르며 정상 fallback 성공을 가정하지 않는다.

[Step 1] 원자 질문 검색과 부모 복원

1. 현재 snapshot·scope·권한·인덱스 fingerprint를 확인한다.
2. 질문 전체를 계약된 설정으로 임베딩한다. 숫자·부정어·기간을 삭제하지 않는다.
3. ATOMIC_TOP_K는 질문 표현 개수 기준이다. 초기 실험 후보는 15이며 고유 원자 수/고유 부모 조문 수와 구분한다.
4. 원자 질문에서 atom revision과 parent ID를 복원한다. 부모 본문은 같은 corpus snapshot에서 가져오며 ID와 hash를 확인한다.
5. 반환 후보와 빈 슬롯 후보를 혼동하지 않는다. 구현상 같은 점수 벡터를 공유하되 다음 목적별 마스크를 적용할 수 있다.
  • 검색/검수 후보: 유효한 검토 원자 질문. 아직 승인 답변이 없는 원자도 포함 가능.
  • 반환 후보: semantic 허용 연결과 활성 답변 revision이 있는 항목. 이 범위를 먼저 제한한 뒤 Top-K를 선택한다.
6. 두 후보 집합을 사용하면 중복 query/atom/parent를 제거하고 실제 총 페어 수를 기록한다. 별도의 임베딩 모델이나 DB를 추가할 필요는 없다. 후보 수 증가는 성능 측정에 포함한다.

이 목적별 후보 분리는 원문의 empty 슬롯 수집과 기존 승인 항목 검색을 함께 유지하기 위한 구현안이다. 생성되지 않은 원자가 있다고 기존 법령 검색을 제외하지 않는다.

질문 벡터는 기존 RAG의 입력·prompt·모델 fingerprint·길이 처리까지 같을 때만 재사용한다. 다르면 별도 인코딩하고 추가 비용을 기록한다.

[Step 2] 그룹별 리랭커 호출과 점수 매핑

|그룹|입력 페어                |작업                               |
|--|---------------------|---------------------------------|
|A |사용자 질문 + 후보의 부모 조문 원문|해당 근거의 관련성                       |
|B |사용자 질문 + 후보 원자 질문    |승인된 범위에서 답변 재사용을 검토하기 위한 질문 관계 신호|

Group B를 단순 문서 검색 점수와 동일한 의미로 취급하지 않는다. 의도·조건 충돌은 §3.3이 별도로 검사하며, Group B 점수는 그 검사를 대체하지 않는다.

각 페어에 pair_id, task_type, 원자/질문/parent ID와 revision, 입력 hash, instruction/version을 붙인다. 리랭커 결과는 순서만 믿지 말고 ID로 결합한다.

• 페어별 작업 지시를 실제 API가 지원하고 평가 계약이 같으면 A/B를 한 배치 요청에 담는 것을 우선 시험한다.
• 지원하지 않으면 task별 두 요청 또는 API 확장을 사용한다. 호출 수를 줄이려고 서로 다른 작업 지시를 하나로 뭉개지 않는다.
• raw logit, 정규화 score 등 점수 형식·범위·변환을 fingerprint에 고정한다.
• A 점수와 B 점수를 직접 더하거나 한 순위로 합치지 않는다. 각각 별도의 threshold를 검증한다.
• 응답 ID·개수 불일치, 오류, NaN/Inf, 필수 입력 잘림은 cache hit에 쓰지 않는다.
• 토큰 제한 때문에 조건·단서가 잘린 parent나 질문을 완전한 검증 입력으로 간주하지 않는다.
• batching의 HTTP 요청 수, 실제 모델 호출/micro-batch 수, 페어 수·토큰 수를 따로 기록한다.

“단일 패스” 목표는 이 단계의 A/B 호출 최적화에만 해당한다. 미스 후 합집합 RAG 리랭킹까지 전체 요청 1회로 끝난다고 약속하지 않는다.

[Step 3] 선택한 동일 원자에 대한 캐시 게이트

후보를 점수순으로 고를 때 같은 답변 revision·같은 재사용 정책의 여러 표현은 중복 경쟁 답변으로 세지 않는다. 대표 질문과 그 정책을 함께 유지한다. 다른 조건 정책을 섞어 높은 점수와 느슨한 조건을 각각 가져오지 않는다.

서로 다른 답변의 질문 관계 점수 차이와 동점/모호성 정책을 val에서 결정한다. Top-K가 한 답변의 별칭으로만 찼다는 이유로 경쟁 답변이 전혀 없다고 판단하지 않는다. 필요하면 검색 후보를 확장해 다른 답변을 확인하거나 모호성 미확인으로 우회한다. 후보가 실제 하나뿐이면 margin을 무한대나 정답 확률로 표시하지 않는다.

선택한 후보의 근거 점수는 반드시 다음 값이다.

selected_atom = 선택한 질문-원자-답변 연결의 원자
linked_parent_score =
    group_A_scores[selected_atom.parent_chunk_id, parent_hash, corpus_snapshot_id]

전역 조문 1위의 점수를 대신 쓰지 않는다. 선택 원자의 parent 점수가 없으면 미스다. 전역 조문 1위와 선택 원자의 parent가 반드시 같아야 하는 것은 아니다.

최종 반환 조건은 모두 AND다.

1. 현재 namespace·권한·scope·snapshot·정책이 후보와 맞다.
2. 해당 답변 revision은 관리자 승인되어 활성 release에 포함되어 있다.
3. 해당 연결의 semantic_enabled와 재사용 범위가 승인되어 있다.
4. 선택 원자의 linked_parent_score가 검증된 parent threshold를 넘는다.
5. 선택한 질문 페어의 score가 검증된 질문 관계 threshold를 넘는다.
6. 의도·필수 표현·구조화 조건이 맞고, 충돌·누락·미지원 추가 조건·미지원 복합 질문이 없다.
7. 서로 다른 답변 간 모호성 정책을 통과한다.
8. 전체 표시·의존 근거와 answer/atom/policy revision이 유효하다.
9. 반환 결정 직전 활성 배포·철회 상태를 재확인한다.

어느 조건이든 실패하면 캐시 미스다. 첫 후보가 실패했을 때 낮은 순위 후보의 느슨한 정책을 계속 시도해 통과시키는 동작은 초기 구현에 넣지 않는다.

0.75와 0.85는 각각 A/B의 실험 시작 후보다. 기존 대화의 cosine 0.95와 같은 척도도, 재사용 정확도 백분율도 아니다. cosine 임계값을 별도 사용한다면 그 역시 val에서 선택하고 calibration에 남긴다.

[Step 4-A] 정확/시맨틱 캐시 반환

반환할 answer revision과 근거는 승인된 같은 버전으로 묶는다. 기존 후처리 중복을 피하고, 최종 표시 정책을 exact와 semantic에 공통 적용한다.

기존 SSE의 답변·근거·완료 이벤트를 유지하며 캐시 hit도 정상 완료 이벤트를 보낸다. 프론트엔드가 답변 출처 때문에 별도의 내용을 조립할 필요가 없도록 한다.

피드백은 실제 사용자 질문, 실제 반환 answer revision, source_type=exact/atomic_semantic/rag, release·snapshot에 연결한다. 원자 대표 질문으로 사용자 질문을 대체 기록하지 않는다.

[Step 4-B] 두 캐시 미스: 기존 검색과 합집합 RAG

1. 기존 조문 검색을 독립적으로 실행한다. 원자 검색에서 나온 부모 ID만을 범위로 삼지 않는다.
2. 유효한 원자 후보의 부모 조문을 추가한다. 미승인 답변에 연결된 원자라도 검색용 원자·부모의 검토/버전/권한이 유효하면 근거 후보로 사용할 수 있다.
3. 다음 집합을 구성해 RAG 리랭킹 인터페이스에 넘긴다.

D_base   = 기존 검색이 제공할 조문 후보
D_atomic = 같은 snapshot의 유효한 원자 부모 조문 후보
D_union  = dedupe_by(snapshot, article_or_chunk_id, content_hash)(D_base ∪ D_atomic)

동일 ID에 다른 본문 hash가 섞이면 임의로 하나를 선택하지 않는다. 버전 충돌로 해당 원자 후보를 제외하거나 요청 snapshot을 다시 구성한다.

4. 후보 예산이 필요해도 원자 후보 때문에 D_base를 조용히 삭제하지 않는다. 기존 후보를 우선 보존하고 추가 원자 수를 제한하거나 micro-batch 처리한다.
5. 합집합을 같은 RAG relevance 계약으로 점수화하고 최종 후보를 선택한다. 기존 하위법령·보충 조문 정책과 전체 토큰 예산을 유지한다. 상세 적용 위치는 실제 코드에 맞춰 정한다.
6. 기존 시스템 프롬프트·모델·생성·인용 정책으로 답변을 생성한다. parent 하나가 선택됐다고 답변을 그 원자 한 문장에 제한하지 않는다.

앞 단계 점수의 재사용 조건

Group A 점수를 재사용하려면 모델·instruction/task·점수 변환·query/문서 원문·truncation·snapshot fingerprint가 모두 같고, 후보 목록에 독립적인 pointwise 계산임이 확인되어야 한다. 이 조건이면 논리적으로 D_union 전체를 평가하되 이미 계산된 페어는 재사용하고 새 페어만 추론할 수 있다.

목록에 따라 바뀌는 점수, 다른 instruction, 다른 입력 길이, Group B 점수는 RAG 점수로 재사용하지 않는다. 불확실하면 합집합 전체를 다시 리랭킹한다. 재사용을 이유로 새 조문 후보를 평가하지 않는 것은 금지한다.

원자 인덱스 오류·없음·구버전이면 D_atomic을 사용하지 않고 기존 RAG로 돌아간다. 다만 공유 리랭커 자체가 실패했다면 기존 서비스의 명시적인 오류·대체 정책을 적용한다.

[Step 4-C] 생성 후 pending 자동 제출

원문의 자동 후보 수집 기능은 유지한다. AUTO_STAGE_PENDING이 켜졌을 때만 작동하며, 제출은 생성 완료 후 수행한다.

다음을 모두 만족할 때 검수 후보로 제출한다.

• 검색 원자와 부모가 유효하고 지원하는 단일 의도·조건 정책에 적합하다.
• 선택한 원자의 A/B 점수와 조건 검사를 통과했다. 승인되지 않았다는 이유로 캐시 미스인 빈 슬롯 등이 대상이다.
• 생성이 정상 종료됐다. 길이 제한 잘림·오류·취소·불완전한 SSE 생성·부적합한 거절은 제출하지 않는다.
• 답변의 근거 ID가 생성 컨텍스트와 해당 snapshot에서 확인된다.
• 개인정보·개별 사건 의존 내용을 공용 후보로 제출하는 정책을 통과한다. 확인 불가 시 기본은 제출하지 않거나 별도 비공용 검토 큐로 격리한다.
• 평가 트래픽이 아니고, 보호 val/test 질문과 충돌하지 않으며, 수집 권한·보존 정책이 정해져 있다.
• 같은 atom/snapshot/제안 정책 슬롯에 기존 pending·hold·rejected·배포 답변을 자동 덮어쓰지 않는다.

후보에는 실제 질문, 대표 원자 질문, 제안된 재사용 범위, 답변, 전체 생성 근거·hash, 모델/프롬프트·완료 정보, snapshot·점수·조건 결과를 기록한다. 이 정보는 승인 자료이지 정답 증명은 아니다.

실제 사용자에게 맞는 생성 답변이 공용 재사용에도 적합하다고 자동 일반화하지 않는다. 관리자가 공용 문구로 수정하면 새 candidate revision을 만들고 변경된 내용·조건을 확인한다.

pending에 넣었다는 사실은 현재 사용자에게 반환한 RAG 답변을 사전 검수했다는 뜻이 아니다. 이후 캐시 재사용을 승인 전까지 막는 정책이다.

새 사용자 질문을 자동으로 exact 별칭 또는 semantic 질문 인덱스에 넣지 않는다. 후보 수집과 train/val 분할·캐시 질문 승인·인덱스 편입은 별개다. 미분할 질문은 후보로 보관할 수 있지만 등록·학습에는 명시적 분할/보호 검사를 거쳐야 한다.

4.2 동시성 및 요청 중 버전 변경

모델 생성 동안 SQLite 쓰기 트랜잭션을 유지하지 않는다. 종료 후 예상 slot 상태·candidate revision·snapshot을 조건으로 짧은 트랜잭션에서 저장한다. 같은 빈 슬롯을 본 두 요청 중 하나만 기록하고, 다른 요청은 충돌 사실만 남긴다.

승인은 관리자가 읽은 candidate revision/hash와 현재 값이 같을 때만 성공한다. 변경·중복 승인 요청은 충돌 또는 멱등 처리하고 새 내용을 보지 않은 승인으로 만들지 않는다.

배포·철회·법령 활성 전환 뒤 구 worker의 인덱스만 믿고 반환하지 않는다. 응답 시작 전 최종 상태를 재검사한다. 검사 시 버전이 바뀌었으면 구 캐시를 포기하고 현재 정책의 RAG 재시작 또는 명시적인 재시도 처리로 전환한다. 새 근거와 구 답변을 섞지 않는다.

4.3 off / shadow / on

|모드      |정확 미스 이후                      |사용자에게 반환        |자동 pending         |
|--------|------------------------------|----------------|-------------------|
|`off`   |새 원자/시맨틱 검사를 생략               |기존 RAG          |새 기능 경로에서는 하지 않음   |
|`shadow`|후보·조건·점수·would-hit를 측정        |기존 RAG 기준선      |기본 금지. 평가 모드는 항상 금지|
|`on`    |검사 통과 시 semantic, 미스 시 합집합 RAG|승인 캐시 또는 합집합 RAG|별도 스위치·수집 조건 충족 시만 |

shadow의 가상 hit를 실제 LLM 호출 절감에 넣지 않는다. 합집합 검색도 shadow에서 평가할 수 있지만, 비교 목적의 리랭킹·후보가 사용자용 기존 컨텍스트를 바꾸지 않도록 분리한다. shadow의 추가 호출 비용도 보고한다.

on에서 미스 후 합집합 RAG를 사용한다는 사용자 결정은 확정이다. 따라서 출시 전 캐시 게이트뿐 아니라 합집합이 기존 검색·답변 품질을 악화시키지 않는지도 평가한다. semantic을 off로 롤백하면 기존 exact와 원래 RAG로 복귀한다.

정확 캐시 on/off와 시맨틱 상태는 독립적이다. 두 기능 모두 off이면 원래 RAG, 정확만 on이면 exact 후 원래 RAG다. 시맨틱만 on인 구성도 운영자가 명시적으로 설정하면 허용하되, 기본 권고 순서는 exact 우선이다.

5.2 조문 개정·시행 시점·철회

초기 기본 정책은 활성 corpus snapshot 불일치 시 구 시맨틱 캐시 전체 우회다. 부모 조문 해시가 같다는 이유로 자동 carry-forward하지 않는다.

개정 시 검토 단위는 조문·의존 근거 → 원자 명제 → 원자 질문 → 인덱스 → 답변/조건 정책 → 승인/release다. 영향을 받지 않은 항목은 새 snapshot에 대한 검증 이력을 만들고 재사용할 수 있지만, 무조건 재생성하거나 무조건 유지하지 않는다.

입법예고 수집은 현행 캐시 교체가 아니다. 장래 시행 snapshot은 별도 준비하고 활성 시점에 corpus·cache release·index의 호환성을 함께 확인한다. 오래된 답변에 최신 근거만 붙이는 것을 금지한다.

유효기간은 명시적 시간대를 사용하고 valid_from ≤ 기준시각 < valid_until로 검사한다. TTL은 버전·철회 검사를 대신하지 않는다. “올해”, 과거 사건, 적용 시점이 불명확한 질문은 지원 정책이 없으면 캐시를 우회한다.

특정 답변·binding·정책의 오류가 확인되면 해당 활성 항목을 철회하고 다음 조회부터 차단한다. 구 인덱스 재로딩을 기다려서만 차단하는 방식은 피한다.

5.3 로그·개인정보

기본 운영 로그에 사용자 질문 원문이나 생성 답변 전체를 무조건 기록하지 않는다.

기본 계측 필드는 다음과 같다.

request_id, mode, source_type, cache_decision, bypass_reason
scope, corpus_snapshot_id, release_id, index_revision
atom/query/answer/policy revision
embedding/reranker/calibration fingerprint
linked_parent_score, question_match_score, margin, condition_status
candidate_query_count, unique_atom_count, unique_parent_count
base_candidate_count, union_candidate_count, rerank_pair_count
reranker_http_calls, model_micro_batches, rerank_tokens, reused_pair_count
exact_ms, embedding_ms, atomic_search_ms, condition_ms
semantic_rerank_ms, rag_search_ms, union_rerank_ms
first_output_ms, completion_ms, pending_stage_result

검수용 실제 질문·답변은 별도 제한 저장소/필드와 보존 정책을 적용한다. hash도 민감성을 완전히 제거한 것으로 취급하지 않는다. 마스킹 때문에 의미·조건이 바뀌었다면 자동으로 공용 승인하지 않는다.

우회 사유는 최소한 not_approved, not_released, semantic_disabled, condition_missing, condition_conflict, unsupported_query, ambiguous_candidates, parent_score_missing, score_contract_error, truncated_input, stale_index, corpus_mismatch, citation_missing, revoked, deadline_exceeded를 구별한다. 실제 서비스 사유 코드가 있으면 호환 매핑한다.

5.4 지연시간·호출 예산

원문의 약 0.1초·1.5초·2~3초는 실측 보장이 아니라 비교할 목표 후보로 남긴다.

7.2 데이터 분할·품질 평가

임계값뿐 아니라 후보 수, instruction, 조건 정책, margin, 허용 범위를 val에서 정한다. 기존 보호 test 및 그 변형을 seed·정책 선택·질문 생성 참고 자료로 사용하지 않는다. 기존 650개를 포함해 프로젝트의 모든 보호 test는 동일 원칙을 적용한다.

평가 입력의 답변 재사용 라벨은 reusable / not_reusable / uncertain으로 관리한다. uncertain을 통과시키지 않는다. 문서에서 생성한 검색용 질문과 train/val/test 답변 캐시를 구분한다. 원자 질문이 보호 질문과 중복·근접 중복되면 누수를 검사하고 평가 구성을 기록한다.

새 피드백은 자동으로 학습 정답이나 val 정답이 되지 않는다. 검토·중복/변형 계열 검사·분할 확정 이후 다음 학습에 반영한다. 평가 실행에서 캐시 예열이나 온라인 alias 등록은 금지한다.

비교할 조건은 기존 exact+RAG, semantic shadow, semantic on+합집합 RAG다. 검색 평가는 기존 후보 대비 추가 회수한 근거와 최종 Top-K 결과를 따로 본다. 기존 답변 평가의 키워드·인용 지표 및 검색 적중 문항/검색 실패 거절 지표는 실제 기존 코드로 병행하되, 시맨틱 재사용의 정오 라벨을 대체하지 않는다.

7.3 출시 기준

• 버전·권한·철회·근거·pending 차단·조건 충돌·ID 매핑 테스트에서 미해결 실패가 없어야 한다.
• 필수 반례와 검토된 uncertain 질문의 오통과가 없어야 한다.
• 법적 결론·수치·대상·조건을 바꾸는 중대한 오재사용은 출시 검토 표본에서 발견되지 않아야 한다. 발견 시 해당 범위를 중단한다.
• 재사용 오류율은 분모·검토 건수·의도별 분포·불확실성을 함께 보고한다. 관측 오류 0건을 확률 0이라고 표현하지 않는다.
• 기존 02 문서의 오류율 단측 상한 1% 제안은 위험 예산의 참고안으로 유지한다. 실제 표본과 상관성을 고려한 출시 기준을 운영자가 확정하기 전 자동 on하지 않는다.
• 정확 hit 성능과 기존 검색 후보가 보존되어야 한다. 합집합으로 후보 재현율이 올라도 최종 검색·답변 품질이 떨어질 수 있으므로 실제 비교가 필요하다.
• 의미 hit의 절감과 miss의 추가 지연을 함께 보고한다. 2~3초 목표 달성 여부는 환경을 고정한 별도 측정이다.
• 운영 법령·출력 정책·승인과 활성 release가 일치해야 한다.

7.4 중단·롤백

중대한 오재사용, 구버전/철회 답변 반환, 개인정보 노출, 데이터 누수, release/index 불일치 또는 지연 예산 초과가 확인되면 semantic을 off로 전환한다.

기존 exact의 유효성 검사와 원래 RAG는 유지한다. 잘못된 answer/binding/policy revision은 별도로 철회하며, 단순 모드 off로 문제 데이터 자체가 수정된 것으로 처리하지 않는다. DB migration·새 인덱스 배포는 이전 활성 manifest와 복귀 절차를 보존한다.

통과 데이터의 원문·분할·판정·복수 표시 근거·hash·출처를 보존한다. pass는 첨부 스냅샷과 해당 질문 연결의 검토 결과다. 새 원자 질문, 다른 문장, 새 법령 버전에서의 자동 재사용 승인이 아니다.

기존 approval_status=not_approved, exact_enabled=false, semantic_enabled=false를 import 중 임의로 뒤집지 않는다. 이미 운영 중인 항목이 있다면 실제 DB의 승인·release를 확인하고 중복 import 또는 전체 덮어쓰기를 피한다.

추후 검토 자료를 승인 seed로 넣지 않는다. 원자 생성에 필요한 법령 원문을 쓰는 것과, 미통과 답변을 정답으로 쓰는 것은 다르다. 노동법 캐시 통과 데이터가 있다고 세법 답변까지 확보됐다고 간주하지 않는다.

10. 남은 확인 사항

Q1. 초기 원자 데이터 생성 범위

아직 사용자 결정이 필요한 범위는 이것이다.

• A안: 통과한 노동법 답변과 연결되는 조문부터 원자를 구축하고 의미 재사용을 시험한다.
• B안: 노동법·세법 전체 조문에 검색용 원자/질문을 먼저 구축한다. 답변이 없거나 미승인인 원자는 검색·pending 수집용으로만 사용한다.

초기 검수·평가 규모를 줄이려면 A안을 제안한다. 다만 원문의 장기 목표는 노동법/세법이므로 B안도 스키마와 런타임에서 지원한다. 이 문서만으로 A를 확정했다고 처리하지 말고, 실제 생성 작업 전 scope manifest를 확정한다.

그 밖의 승인/배포 버튼 동작, 리랭커 페어별 instruction 지원, migration 번호, 모델 버전은 사용자가 추측해 답할 항목이 아니라 §2의 실제 레포 확인 사항이다. 임계값·성능 예산은 val/부하 측정 후 결정한다.
