## 1단계: 상담 전체 추적 저장 (PR 2, 2026-11-24 착수 승인)

목표: 질문부터 답변까지 모든 단계와 모든 모델 호출의 송신·수신 원문을 상담별 순서대로 DB에 남겨, 질문이 어떻게 답변에 도달했는지 따라갈 수 있게 한다(디버깅·평가·학습). A′는 취소됐으므로 판정 호출 기록은 `clarify=True`로 켤 때만 생긴다.

구현에서는 삭제 미리 보기를 관리자 세션·조건·정확한 상담 집합에 묶어 삭제 트랜잭션에서 다시 확인한다. 압축 응답은 원문을 보존하되, 가림 대상이 있으면 압축을 풀고 가린 값을 저장한다. 해석할 수 없는 인코딩은 가림 표식만 남긴다. 실제 모델 시험은 이번 작업 지시대로 실행하지 않았다.

### 저장소와 스키마
- 기존 `LAWBOT_DB`(SQLite, `lawbot-db` 마이그레이션)에 `0003_consult_trace.sql`을 추가한다. 운영 `.env`에는 `LAWBOT_DB`가 있다.
- `consults`: 상담 id(새 uuid), 요청 id(`request_id`, 요청 로그와 연결), 생성·종료 시각(시간대 포함 ISO 8601), 사용자 계정(로그인 이름의 SHA-256 앞 16자)과 역할(user/admin), 세션 id(쿠키 토큰이 아닌 서버 세션 id), 원 질문, 사용자에게 공개된 최종 글, 화면 판정(`answer_verdict`), 상태(ok/error/cancelled)와 오류 유형, 보존 정책 버전(`consult-trace-v1`), 앱 커밋·코퍼스 릴리스·writer system 지문, 피드백 턴 id(있으면), 가림 기록 수.
- `consult_steps`: 상담 id, 순번, 단계(`router`·`search`·`rerank`·`decree_search`·`decree_rerank`·`definitions`·`clarify`·`writer`·`citation`·`display`), 시작·끝 시각, 결과 JSON(검색 질의, 후보와 점수·순위, 최종 제공 조문, 정의·하위법령 첨부, 계산 라우팅 결과, 인용 판정 목록, 표시 판정·표시 글).
- `model_calls`: 상담 id, 순번(상담 안에서 송신 순서), 용도(`embedding`·`rerank`·`router_select`·`router_label`·`clarify`·`writer`), HTTP 메서드·경로, 모델 id·revision(시작 때 `/v1/models`에서 읽은 값), **송신 본문 바이트 그대로**(BLOB), 수신 상태 코드, 수신 본문 바이트(비스트림) 또는 수신 조각 목록(스트림: 받은 순서와 수신 시각 오프셋을 보존), 시작·첫 바이트·끝 시각, usage 토큰, 오류 유형. 요청·응답 헤더는 저장하지 않는다.
- `consult_trace_deletions`: 삭제 시각, 관리자 계정 해시, 조건(사용자·기간), 삭제한 상담 수·단계 수·호출 수. 삭제한 내용은 남기지 않는다.
- `consult_trace_redactions`는 따로 두지 않고 `model_calls`·`consult_steps`에 가린 위치 수와 사유 목록을 함께 저장한다.

### 수집 방법
- 모델 서버 클라이언트(`ModelServerClient`의 `httpx.Client`)와 생성 클라이언트(`openai.OpenAI`에 넘기는 `httpx.Client`)에 송신 바이트와 수신 바이트를 그대로 기록하는 httpx 전송 계층(transport 래퍼)을 붙인다. 앱의 요청 조립 코드는 바꾸지 않는다.
- 상담 경계는 기존 요청 id 문맥(`REQUEST_ID` contextvar)으로 묶는다. 시작 시 조문 인덱스 임베딩, 상태 확인(`/health`, `/v1/models`) 같은 상담 밖 호출은 기록하지 않는다.
- 단계 기록은 `service.ask`가 이미 만드는 값(`st`, hits, 원문)을 모아 상담이 끝날 때(정상·오류·취소 모두) 한 트랜잭션으로 쓴다. 쓰기는 답변 스트림을 막지 않게 하되, 실패하면 요청 로그에 `trace_status=failed`와 예외 종류만 남긴다(원문 없음).
- 설정 `LAWBOT_CONSULT_TRACE`(기본 `1`, `LAWBOT_DB`가 있을 때만 켜짐, `0`이면 끔). `LAWBOT_DB`가 없으면 끄고 시작 로그에 한 줄 알린다. 평가 실행기는 이번 PR에서 바꾸지 않는다(평가는 결과 파일에 이미 원문을 남김).

### 가림
- 저장 직전에 설정된 모델 서버 토큰, 생성 API 키, 모델 서버·생성 서버 주소(호스트:포트), 웹앱 포트, 세션 쿠키 형식 값을 찾아 그 부분만 `[REDACTED:<사유>]`로 바꾸고 사유를 기록한다. 질문·답변 본문의 개인정보는 가리지 않는다(사용자 고지로 대체).

- 실상담 화면: 입력창 근처에 "상담 내용은 디버깅·평가·학습을 위해 기한 없이 보관되며, 관리자에게 삭제를 요청할 수 있습니다." 고지(추적 저장이 켜졌을 때만, `/api/config`로 전달).

### 시험
- 계약: 대역 생성 서버·모델 서버 앱이 받은 요청 바이트와 돌려준 본문(스트림은 조각 순서)을 DB 저장값과 순서대로 바이트 단위로 대조. 상담 밖 호출이 기록되지 않음. 가림(토큰·주소·포트·쿠키). 오류·취소 상담도 기록.
- 단위: 마이그레이션 적용·checksum, 삭제 조건(사용자·기간)과 건수 기록, 설정(`LAWBOT_DB` 없음·`LAWBOT_CONSULT_TRACE=0`), 요청 로그에 원문이 없음.
- 대역 E2E(브라우저): 로그인 → 질문 → 답변 → 관리자 화면에서 그 상담의 단계·호출 원문 확인 → 삭제 → 건수 표시. 실상담 화면 고지 표시.
- 실제 모델 E2E는 웹앱 기록 경로만 바뀌므로 `e2e_live` 3개를 승인 후 실행하고, 시험 DB에 기록된 호출 수·바이트를 확인한다.

### 운영 반영(별도 승인)
- 운영 DB 백업 → `lawbot-db` 마이그레이션 0003 → 웹앱 재시작 → 실제 질문 없이 상태 확인. 버전 Y 올림(DB 스키마 마이그레이션).

## 2단계: 인용 품질 (A·A′ 공통)

0단계 근거: 미확인 인용 노출은 결론 본문에서만 생겼다(제공되지 않은 조문 인용, 본문 상호참조를 법령명 없이 옮김, 미등록 법령명).

- writer system 보강(`data/v5/system_v5_concise.txt`): 조문은 항상 법령명과 함께, 참고 조문에 없는 조문은 결론에서 인용하지 않음, 조문 본문 속 "제N조에 따른" 상호참조는 법령명을 붙여 풀어 쓰거나 인용하지 않음, 【근거 조문】에는 받은 조문만.
- 결론 본문 판정: 등록 별칭에 없는 법령명(예: 사회복지사업법, 「…법」)도 법령명으로 인식해, 그 뒤 번호를 앞 법령에 붙이지 않고 "제공되지 않은 다른 법령"으로 판정한다. 법령명 없는 번호는 같은 문장 또는 직전에 명시한 법령, 또는 제공 조문 중 유일한 번호로 확실히 귀속될 때만 인정. "법 제N조"·"같은 법"은 직전 법령으로 귀속. 시행령·시행규칙은 법률과 구분.
- 표시 정책(2026-11-24 사용자 결정: **표시**): 결론·근거의 확인되지 않은 인용(outside·nonexistent·wrong_law·귀속 불가)은 답변 전체를 막지 않고, 근거 카드를 만들지 않으며, 인용 바로 뒤에 "⚠확인되지 않은 인용" 표시를 붙인다. 현행의 `invalid_citation` 차단은 이 표시로 바꾼다. 확인된 인용이 하나도 없으면(`missing_citation`) 현행처럼 안내한다. "제거"는 문장이 깨질 수 있어 택하지 않았다.
- 검색은 바꾸지 않는다(2026-11-24 사용자 결정). 참조 조문 1단계 확장, 되묻기 답을 넣은 재검색은 이번 범위에서 제외하고 후속 후보로만 남긴다.
- PR 1 리뷰 반영: 법령 인식과 번호 귀속을 분리하고 귀속 근거를 기록한다. 선행사는 같은 문장·직전 문장으로 제한하며 근거 목록은 각 줄을 독립 판정한다. 병렬 법령·항목, 인용 괄호, 부칙과 줄바꿈까지 포함한 원문 위치를 독립 기대표로 대조한다. 계산기가 검증한 근거는 인정하되 검색 카드로 만들지 않는다.
- PR #193 추가 리뷰: 미등록 법령 후보는 조문 번호·인용 부호·법률 제목·하위법령처럼 인용 근거가 있는 형태로 제한한다. 일반어가 기존 귀속을 덮어쓰지 않고 실제 미등록 인용은 여전히 `outside`인지 독립 기대표로 검증한다.

## 3단계: 입력 한도 (변경 없음)

0단계에서 입력 한도 초과·잘림이 없었다(최대 9,895토큰, 전부 `stop`). Lawbot2에서 한도를 넘은 T09182·CARD01·CARD02·FACT009도 정상 종료했다. 코드는 바꾸지 않고, A·A′ 평가에서 입력 토큰 최대값만 계속 기록한다.

## 4단계: A′ 되묻기 1회 (취소, 2026-11-24)

구현·평가 후 판정 기준 3개 불통과로 취소했다. 설계·결과·재시도 방법은 [기록](clarify-a-prime.md)에 있다. 아래는 구현 당시 계획이다.

0단계 근거: 사실 부족 15건 중 확인 질문 0건, 빠진 사실을 묻지 않고 단정 5건.

- 검색이 끝난 뒤 writer 전에 판정 호출 1회(비스트리밍, `enable_thinking=False`, 출력 상한 작게). 입력: 원 질문, 제공 조문 목록(법령명·조문·제목·발췌). 출력 엄격 JSON `{"ask": bool, "missing": [...], "question": "..."}`; 형식 오류는 1회만 재요청.
- `ask=true`면 서비스가 `clarify` 단계로 확인 질문과 확보한 조문을 돌려주고 생성을 멈춘다. 답으로 재개하면 같은 조문을 writer에 주고, 입력에는 원 질문 → 확인 질문 → 답을 넣는다. 재검색하지 않고 상담당 최대 1회.
- 판정 실패·형식 오류가 끝내 나면 A와 같은 흐름으로 writer 진행(fail-open)하고 사유를 기록한다(요청 로그에는 판정 결과·사유·호출 수·토큰만, 원문은 넣지 않음). 계산 질문은 이 단계를 건너뛴다.
- 판정 system 프롬프트는 별도 파일(`data/v5/system_clarify.txt`), 지문을 평가 기록에 남긴다(PR 2 뒤에는 추적 저장에도). PR 1에서는 서비스의 명시적 `clarify=True` 인자만 사용한다(기본 꺼짐). `LAWBOT_CLARIFY_ENABLED` 설정과 웹 연결은 A′ 채택 뒤 별도 PR.
- 재개: `service`에 판정 결과를 돌려주는 단계와, 확보한 조문·확인 질문·사용자 답으로 writer만 실행하는 재개 함수를 둔다(재검색 없음). 웹 API·화면 연결은 A′ 채택 뒤 별도 PR.
- 평가 실행기(`tools/lawbot-tools`): 세트 JSON을 읽어 A·A′를 같은 문항으로 실행하고, 문항별로 제공 조문, 판정 호출의 송신 `messages`·수신 원문·파싱 결과, writer 원문, 화면 판정·표시 글, 결론·근거 인용 판정, 단계별 시간·토큰을 결과 파일에 남긴다. 사실 부족 문항에서 A′가 물으면 `missing_facts`만 보고 미리 써 둔 고정 가상 답(한 문장)으로 재개해 최종 답까지 기록한다. 06:00 정지·07:00 재개, 실행 전후 구성 확인을 포함한다.
- 시험(대역): ask=false면 writer 입력이 A와 바이트 단위로 같음, ask=true 재개 시 writer 입력에 원 질문 → 확인 질문 → 답 순서, 형식 오류 1회 재요청, fail-open, 상담당 1회, 계산 질문은 판정 생략.
- PR 1 리뷰 반영: 최종 `lookup`은 판정하며 계산·안내는 건너뛴다. `stop` 본문의 JSON·스키마 오류만 재요청한다. 확인 질문에도 인용 표시를 적용하고 모든 표시 턴을 노출 지표에 합산한다. 판정 호출 오류는 정상 writer 채점과 분리하고 3회 연속이면 중단한다.

## 평가 (구현 뒤, 별도 승인)

- 조건: 0단계 기준선 → 2·3단계 적용 A → A′. 같은 문항 짝으로 개선/악화/동일. Lawbot2 A/B는 참고값.
- 평가 실행기: `tools/lawbot-tools`에 세트 JSON을 읽는 실행기를 추가하고, 세트는 `data/eval/m5/`에 넣어 재현 가능하게 한다(출처·해시는 세트의 `meta` 그대로).
- PR 1 리뷰 반영: 호환 캐시만 읽고 인덱스 추론은 하지 않는다. 매 추론 송신 직전에 중단 여부를 확인하고 단계별 송신·종료를 저장한다. 강제 종료 뒤에는 미검증 구간을 무효로 기록하고 이미 송신한 문항은 다시 보내지 않는다. 실패 진단에는 단계·요청 ID·예외 타입·HTTP 상태만 기록한다.
- PR #193 추가 리뷰: M5는 화면에 `missing_citation` 안내만 표시된 답변을 미응답으로 채점하고 검색 적중 집계는 유지한다. 대역 회귀 시험 후 기본 전체·Ruff·Pyright를 실행한다.
- 판정 프롬프트 조정은 `fact_missing`·`reasoning`만 보고 한 번까지. 조정하면 새 사실 부족 15문항을 따로 작성해 최종 확인.
- 판정 기준(2026-11-24 소유자 확정, 실행 전 고정): 미확인 인용 노출 0건 · 사실 부족 확인 질문률 ≥ 50% · 일반·추론 불필요한 되묻기 ≤ 3% · `general` `total`·`reasoning` `cite_ok` 짝 기준 악화 ≤ 개선 · 검증된 답변까지 p95 ≤ 60초이고 A 대비 p50 증가 ≤ 5초 · 판정 실패 ≤ 2%.

## 완료 기준

- 기본 테스트 전체(단위·계약·통합·대역 E2E)와 Ruff·Pyright·화면 typecheck·test·build 통과.
- A·A′ 평가와 `e2e_live` 3시나리오는 구현 검증과 분리한다. PR 1 구현 중 실제 모델은 호출하지 않는다. 오케스트레이터가 별도 승인 뒤 실행하고 시작·종료 구성과 결과를 `docs/evals/`에 기록한다.
- 운영 반영(마이그레이션 포함)은 별도 승인.

## 지시문과의 차이

- 지시문은 "측정 후 계획서"이지만 저장소 규칙상 평가도 계획서 대상이라, 0단계만 확정하고 나머지를 초안으로 둔 이 문서를 먼저 쓴다.
- 이 저장소는 【근거 조문】 미확인 인용이 있으면 화면에서 이미 답변을 막는다(위 표). 표시 정책 변경은 이 차단을 완화하는 변경이기도 하다.
