## 1. 목표와 기본 원칙

1. 챗봇의 법령 코퍼스, 피드백, 사람 검수 이력, 학습·평가 데이터셋 메타데이터를 **SQLite lawbot.db**에서 일관되게 관리한다.
2. 법령 캘린더는 기존 독립 DB와 공개 읽기 전용 서비스를 유지한다.
3. 운영 챗봇의 법령 원문 조회 기준은 SQLite로 전환한다. 기존 CSV는 초기 이관·검증·버전별 학습 스냅샷 및 법령 생성기 중간 산출물로 허용하되, 운영의 동등한 원본을 이중 관리하지 않는다.
4. 임베딩 검색은 우선 기존 NumPy 행렬·.npz 캐시를 유지한다. 벡터 캐시는 SQLite에 기록된 법령·모델 버전으로부터 재생성 가능한 파생 데이터로 취급한다.
5. 피드백은 자동 정답이 아니다. 사람 검수 및 데이터 누출 검사를 통과한 항목만 학습 후보로 승격한다.
6. 기존 고정 Test를 학습·설정 선택에 사용하지 않는다. Train·Val 간 동일·유사 질문 중복을 방지한다.
7. 기존 법령 자동 갱신의 검증·배포·롤백 기능과 기존 서비스 경계를 보존한다.
8. 모든 데이터 변경은 출처, 버전, 승인자, 변경 시점, 재현 가능성을 남긴다.
9. 개발·테스트·운영 DB, 캐시, 피드백과 스냅샷 경로를 분리한다. 사용자 질문 원문은 공개 저장소에 커밋하지 않는다.

### 2.1 서비스

| 서비스 | 역할 | 공개 범위 | 요구사항 |

## 3. SQLite 데이터 모델

### 3.1 공통 저장소 요구사항

- SQLite 파일은 챗봇의 법령 원문·피드백·검수·QA 데이터의 단일 기준 저장소다. 캘린더 DB는 별도 유지한다.
- PRAGMA foreign_keys=ON, WAL 모드, 적절한 busy_timeout, 스키마 버전 마이그레이션을 적용한다.
- 쓰기 트랜잭션은 짧게 유지한다. 모델 추론·임베딩 생성·외부 API 호출을 쓰기 트랜잭션 안에서 실행하지 않는다.
- 스키마 변경은 명시적 마이그레이션으로만 수행하며, 시작 시 운영 DB를 묵시적으로 생성·초기화하지 않는다.
- 데이터 조회 계층을 법령, 피드백, 데이터셋으로 분리하고 SQLite 구현을 API/도메인 로직에 직접 퍼뜨리지 않는다.
- DB 백업·복구 절차는 WAL을 고려한 안전한 방법을 사용하며, 실제 복원 테스트를 제공한다.
- 원본 질문과 답변이 들어 있는 DB·백업·내보내기 파일은 Git 제외, 최소 권한, 보존·삭제 정책을 적용한다.

### 3.2 법령 코퍼스

논리 테이블(물리 테이블명·정규화 수준은 plan.md에서 확정):

- laws: 안정적인 법령 식별자, 공식 명칭, 법령 종류, 출처.
- article_versions: 법령 식별자, 조문 번호·제목·본문, 버전 키, 원문 해시, 기준일·시행일, 개정/삭제 상태, 수집 출처와 커밋, 유효 범위.
- corpus_releases: 코퍼스 릴리스 ID, 기준일, 출처 참조, manifest 해시, 생성·검증·활성화 상태.
- corpus_release_articles: 릴리스별 포함 조문 및 검색 대상 여부.
- active_corpus: 현재 활성 릴리스 식별자.

요구사항:

1. 동일 법령·조문 번호의 과거/현재 버전을 보존할 수 있어야 한다. 조문 번호만으로 전역 유일성을 가정하지 않는다.
2. 법률·시행령·시행규칙을 구별하고, v4·v5의 범위 및 하위법령 첨부 기능을 유지한다.
3. 입법예고·시행 예정 조문을 현재 시행 중인 법령과 혼동해 검색하지 않는다. 기준일과 시행일·경과조치 판단 규칙은 기존 생성기와 일치해야 한다.
4. 원문, 삭제 상태, 문서 생성 문자열을 마이그레이션 전후 대조한다. 기존 retriever.doc_text의 문서 형식을 임의로 바꾸지 않는다.
5. articles_v5.csv만이 아니라 현재 운영 v4 법률/하위법령 조합과 v5의 범위 확장 자료를 각각 식별해 보존한다.
6. 법령 변경은 새 릴리스에 먼저 반영하고 검증 후 활성 릴리스를 전환한다. 기존 릴리스는 롤백할 수 있어야 한다.

### 3.3 벡터 인덱스와 캐시

- 현재 services/chatbot/src/lawbot/embed_cache.py의 NumPy 기반 검색과 .npz 캐시를 초기 구현에서 유지한다.
- 캐시 메타데이터는 corpus_release_id, 임베딩 모델 ID/revision, 문서 포맷·max_seq, 벡터 차원, 문서 해시, 조문 ID 순서 및 캐시 해시를 포함한다.
- 변경된 조문만 재임베딩할 수 있으나 .npz를 제자리에서 부분 수정하지 않는다. 새 전체 행렬과 ID 매핑을 임시 파일로 작성하고 검증 후 원자적으로 교체한다.
- 모델 변경, 문서 형식 변경, 조문 순서 변경 시 기존 캐시를 잘못 재사용하지 않는다.
- 질의 처리 시작 시 선택된 코퍼스 릴리스와 벡터 세트가 응답 종료까지 일치해야 한다.
- 임베딩 차원은 실제 모델 출력으로 검증하며 1024 등 상수를 스키마의 불변 사실로 가정하지 않는다.
- sqlite-vec 전환은 이번 구현의 필수 범위에 넣지 않는다.

### 3.4 피드백 및 검수

논리 테이블:

- feedbacks: feedback_id(유일), turn_id, 제출 시각, label(like/flag/cleared 등 기존 값), reason, 원본 질문, answer_raw, answer_shown, 참고 조문·검색 결과·인용 판정·모델·프롬프트·코퍼스 버전·request ID·프로필 등 당시 컨텍스트.
- feedback_reviews: 검수 이력 ID, 피드백 ID, 검수자, 판정(correct/incorrect/uncertain 등), 범위 판정, 근거 조문, 교정 질문·답변, 메모, 시각.
- feedback_promotions: 승격 ID, 피드백 ID, 연결된 QA 항목, 승격 종류, 승인자, 시각, 스냅샷 반영 상태.
- audit_events: 관리자 변경의 행위자, 대상, 작업 종류, 시각, 변경 요약.

요구사항:

1. 기존 feedback/feedback_YYYY-MM.jsonl의 모든 필드를 손실 없이 이관할 수 있어야 한다. 스키마화하지 않은 원본 컨텍스트는 원본 JSON 형태로 보존할 수 있다.
2. 기존 like, flag, cleared 및 retrieval, answer, false_refusal, other 등의 의미를 보존한다. flag를 단순히 down으로 바꿔 오류 유형을 잃지 않는다.
3. 피드백 원본은 수정하지 않고 검수·승격을 별도 이력으로 기록한다.
4. 좋아요는 정답을 의미하지 않는다. 싫어요/문제 신고도 반드시 오답을 의미하지 않는다.
5. 원본 답변과 화면 표시 답변을 구분하고, 실제 생성 답변과 후처리된 참고·벌칙 문구의 차이를 보존한다.
6. 동일 피드백 중복 승격 방지, 재시도 멱등성, 승인 취소·보류·반려 상태를 지원한다.
7. 기존 피드백 선택 해제(cleared) 및 최신 상태 계산 규칙을 이관 후에도 유지한다.

### 3.5 QA 데이터셋 및 분할

논리 테이블:

- qa_items: 안정적 QA ID, 질문, 유형, 출처, 법령·정답 조문 연결, 생성·검수 상태.
- answer_keys: 정답 ID, 모범 답변, 키워드 그룹, 금지 표현, 근거 조문, 버전.
- qa_splits: QA ID, 데이터셋 버전, 목적(embedding/sllm/reranker 등), 단일 분할(train/val/test/unassigned), 분할 그룹·시드·규칙.
- qa_preferences: 승인된 정답/비선호 답변 쌍, 검수 판정, 활용 가능 작업.
- dataset_releases: 스냅샷 ID, 기준 코퍼스·데이터 버전, 생성 시각, 파일 목록·해시·분할 요약.

금지: 동일 QA 또는 의미상 중복되는 질문 그룹을 train,val처럼 두 분할에 동시 편입하는 규칙.

요구사항:

1. 기존 qa_tax_v5.csv, split_tax_v5.csv, answer_key_tax_v5.csv의 식별자, 참조 관계, 키워드/금지 표현, 학습 목적별 분할을 보존한다.
2. 임베딩과 sLLM의 분할은 서로 다를 수 있다. 단, 같은 학습 목적의 Train·Val·Test는 서로 겹치지 않아야 한다.
3. 기존 고정 Test는 수정·재분할·학습 편입하지 않는다. 동일/유사 질문 검사에 걸린 피드백은 격리·보류하고 자동 승격하지 않는다.
4. 신규 피드백은 기본 unassigned 또는 승인된 Train 후보로 관리한다. Val 편입은 사전에 정의된 재현 가능한 분할 정책에 따라 별도로 수행한다.
5. 동일·유사 질문은 그룹 단위로 분할한다. 중복 검사는 정확 일치와 기존 feedback_review.py의 유사도 기준을 활용하고, 경계 사례는 검수한다.
6. 기존 Test로 모델·하이퍼파라미터·임계값을 선택하지 않는다. 선택은 Val만 사용한다.
7. 분할 정책, 시드(42), 그룹 키, 적용 시점과 데이터 버전을 스냅샷에 기록한다.

## 4. 인증 및 관리자 API

### 4.1 인증 확장

현재 구현 기준:

- LAWBOT_USER / LAWBOT_PW 자격증명, 서버 메모리 기반 랜덤 토큰 세션, POST /api/login, GET /api/me, POST /api/logout.
- 기존 로그인과 쿠키 속성(HttpOnly, SameSite, HTTPS Secure 조건), 만료·로그아웃 동작을 유지한다.

변경 요구사항:

1. 기존 일반 사용자 자격증명 설정을 하위 호환으로 유지하면서 관리자 계정을 별도 설정한다. 관리자 비밀번호는 안전한 해시·검증 방식을 사용한다. 기존 일반 사용자 비밀번호 해시 전환은 별도 마이그레이션으로 설계한다.
2. 서버 세션에 role: "user" | "admin"을 부여한다. 클라이언트가 전달한 role을 신뢰하지 않는다.
3. 기존 GET /api/me를 확장해 { "user": "...", "role": "user" | "admin" }을 반환한다. 별도 /api/session 생성은 요구하지 않는다.
4. 모든 /api/admin/*는 서버에서 관리자 역할을 검증한다. 비인증 401, 권한 부족 403.
5. 관리자 로그인·승격·교정 API에는 요청 제한, CSRF/Origin 보호, 감사 로그, 입력 크기 제한을 적용한다.
6. 테스트·개발·운영 계정 및 세션을 분리한다. 프론트엔드의 메뉴 숨김은 보안 경계가 아니다.

### 4.2 관리자 API

| API | 목적 |
|---|---|
| `GET /api/admin/feedbacks?status=PENDING&label=like\|flag&cursor=…` | (목록) |
| `GET /api/admin/feedbacks/{feedback_id}` | 당시 질문·답변·참고 조문·검수 이력 상세 |
| `POST /api/admin/feedbacks/{feedback_id}/review` | 판정, 교정 초안, 근거 조문, 보류/반려 저장 |
| `POST /api/admin/feedbacks/promote-up` | 검수 완료된 좋아요 피드백 단건·다건 승격 |
| `POST /api/admin/feedbacks/{feedback_id}/promote-down` | 검수·교정된 문제 신고 답변 승격 |
| `GET /api/admin/calendar-overview` (선택) | 배포상 필요할 때만 기존 공개 캘린더 API를 읽기 전용 프록시 |

POST는 JSON 입력·서버 검증·멱등성 처리를 필수로 한다. 요청·응답 스키마, 배치 성공/실패 의미, 페이지네이션 규칙은 plan.md에서 확정한다.

#### 4.2.1 좋아요 승격

관리자가 선택한 피드백에 대해:

1. 현재 상태, 검수 판정, 근거 조문, 코퍼스 버전, Test/Val 유사도 충돌 여부를 확인한다.
2. 정확성 검증을 통과한 답변만 승격한다. 좋아요만으로 ground_truth_answer=model_answer를 확정하지 않는다.
3. 관리자가 수정한 답변이 있으면 수정본을 정답으로 사용하고 원본을 별도 보존한다.
4. 검증 완료 후 짧은 트랜잭션에서 QA 항목·정답·검수/승격 이력을 생성하거나 연결한다.
5. QA 분할은 train,val로 지정하지 않는다. 기본 미배정/승인된 Train 후보 정책을 따른다.
6. 배치 처리 시 항목별 실패 사유와 성공 결과를 반환하고 재요청으로 중복 승격하지 않는다.

#### 4.2.2 문제 신고 승격

요청 필드(최소): corrected_question, corrected_answer, gold_articles, review_verdict, review_note, 멱등성 식별자.

1. 기존 flag 사유와 원본 질문·답변을 보존한다.
2. 교정 답변과 근거 조문의 정확성을 관리자 검수로 확인한다.
3. 기존 답변이 실제 오답으로 판정된 경우에만 rejected_answer를 비선호 답변으로 기록한다. 단순 불만족/검색 오류/표현 문제만으로 오답 라벨을 붙이지 않는다.
4. 수정 질문·정답·근거 조문·검수 판정·승격 이력을 하나의 트랜잭션으로 기록한다.
5. 분할과 중복 검사 규칙은 좋아요 승격과 동일하게 적용한다.

### 6.3 학습/평가 스냅샷

- tools/lawbot-tools/src/lawbot_tools/export_dataset_snapshot.py
- 실행 예: uv run python -m lawbot_tools.export_dataset_snapshot --version v6 ...

요구사항:

1. 일관된 읽기 시점에서 지정한 dataset_release와 corpus_release를 추출한다.
2. 기존 학습·평가 도구가 기대하는 CSV/JSONL 스키마와 이름을 지원한다. 필요 시 명시적 변환 매핑을 제공한다.
3. qa, answer_key, 목적별 split, articles, 생성 모델 선호쌍, 임베딩 Positive/Negative 페어를 용도에 맞게 분리해 내보낸다.
4. rejected_answer는 생성 답변 비선호 데이터이며, 임베딩·리랭커 Hard Negative 조문으로 직접 사용하지 않는다. 검색 Hard Negative는 검수된 오답 조문을 별도 지정한다.
5. 같은 QA/질문 그룹이 동일 목적의 Train·Val에 중복 출력되지 않아야 한다. 기존 Test는 학습 산출물에서 제외한다.
6. manifest.json에 입력 DB/코퍼스 릴리스, 분할 정책·시드, 모델·프롬프트 버전, 생성 시각, 파일 목록·행 수·SHA256을 기록한다.
7. 기존 스냅샷을 묵시적으로 덮어쓰지 않는다. 동일 버전 재추출은 해시가 같아야 하며 다르면 실패하거나 명시적으로 새 버전을 생성한다.
8. 기존 평가 지표(score_answers.py의 키워드 그룹 × 인용 판정 × 금지 표현 패널티)와 검색 적중 문항 점수·검색 실패 시 거절률을 유지한다.

## 7. 법령 자동 갱신과 운영 전환

기존 law-monitor daily → lawbot-articles-update의 수집·생성·검증·재시작·롤백 흐름을 보존한다. 새 구현은 그 흐름의 검증된 운영 반영 대상을 SQLite 코퍼스 릴리스와 연계한다.

필수 순서:

1. Legalize KR/법제처/국회 소스 변경 감지.
2. 기존 생성기 규칙으로 법령·조문·시행일 파싱 및 새 코퍼스 릴리스 생성.
3. 기존 운영 데이터와 Diff 계산, 변경·추가·삭제 조문 식별.
4. 변경 조문 재임베딩 및 새 전체 검색 행렬·매핑 생성.
5. 원문/캐시 해시, 검색 동등성·핵심 검색 품질, 삭제/시행 상태, API 준비 상태 검증.
6. 검증 성공 시 새 코퍼스 릴리스 활성화 및 서비스의 새 릴리스 로딩. 진행 중 요청의 기존 릴리스 일관성 보장.
7. 실패 시 기존 활성 릴리스·캐시 유지. 필요 시 이전 릴리스로 롤백.
8. 갱신·실패·롤백 결과와 출처/시점/버전을 운영 로그에 기록.

법령 갱신 중 모델 서버를 임의로 재시작하거나 모델 가중치를 교체하지 않는다. 기존 articles_update.py의 보호·복구 조건을 제거하지 않는다.

## 10. plan.md 작성 지침

코딩 에이전트는 이 SPEC를 그대로 구현 지시로 간주하기 전에 다음을 명시한 계획을 작성한다.
