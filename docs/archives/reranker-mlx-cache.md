# 리랭커 MLX 버퍼 캐시 비우기

작성: 2026-11-18

## 문제

v6.3.0 반영(11-18 17:51 모델 서버 재시작) 뒤 약 4시간 만에 운영 모델 서버 메모리가 21GB까지 늘었다. 맥 미니 RAM은 32GB다.

- `footprint`: 늘어난 양은 거의 전부(20GB)가 GPU 메모리(IOAccelerator)였다. 모델 가중치는 리랭커 4bit 2.1GB와 임베딩 fp16 1.1GB뿐이다.
- 그 바람에 스왑이 17.0GB(남은 0.37GB)까지 찼고, 생성 서버(27B) 메모리 15GB 중 14GB가 압축·스왑으로 밀려났다. 이 상태에서는 답변 생성이 느려진다.
- 21:39에 모델 서버를 재시작해 임시로 해소했다. 재시작 후 모델 서버 4.0GB, 스왑 1.5GB다.

## 원인

`services/model-server/src/lawbot_model_server/rerank.py`의 `Reranker.score()`는 문서를 하나씩(batch 1, 패딩 없음) 최대 2,560토큰까지 MLX로 계산한다.

- 문서마다 입력 길이가 다르므로 중간 결과 버퍼 크기도 매번 달라진다.
- MLX는 다 쓴 버퍼를 지우지 않고 버퍼 캐시에 남겨 둔다. 기본 캐시 상한은 메모리 상한(권장 작업 메모리, RAM의 약 75%)과 같다. 크기가 맞지 않아 다시 쓰이지 못한 버퍼가 그 상한까지 계속 쌓인다.
- 모델 서버 코드에는 MLX 캐시를 제한하거나 비우는 호출(`mx.set_cache_limit`·`mx.clear_cache`)이 없다. 임베딩(torch MPS)은 문서를 인코딩한 뒤 이미 `torch.mps.empty_cache()`를 부른다.

## 변경

- `Reranker.score()`가 끝날 때 `mx.clear_cache()`를 부른다. 점수 검증 오류로 끝날 때도 비운다.
- 한 요청 안의 문서 10개는 지금처럼 캐시를 재사용한다. 요청 사이에는 캐시가 남지 않으므로 상주 메모리가 "가중치 + 한 요청의 최대 작업량"을 넘지 않는다.
- 채점 방식(프롬프트, 최대 길이, 로짓, softmax)은 바꾸지 않으므로 점수는 같다.
- `mx.set_cache_limit`(프로세스 전체 상한)는 쓰지 않는다. 상한값을 따로 골라야 하고, 같은 프로세스의 다른 MLX 사용에도 영향을 주기 때문이다.
- `docs/operations.md`의 리랭커 설명에 "요청마다 MLX 캐시를 비움"을 한 줄 적는다.

## 테스트 (TDD)

`services/model-server/tests/test_ms_models.py`(작은 무작위 MLX Qwen3)에 추가한다.

1. Red: `score()` 뒤 `mx.get_cache_memory() == 0`. 현재 코드에서는 캐시가 남아 실패한다. 길이가 다른 문서 여러 개로 확인한다.
2. Red: 점수 검증 오류(`RuntimeError`)로 끝난 뒤에도 `mx.get_cache_memory() == 0`.
3. 기존 점수 테스트(같은 입력은 같은 점수 등)가 그대로 통과한다.
4. 기본 테스트 전체, 린트, 타입 검사를 통과한다.

## 완료 기준

- 위 테스트와 기본 테스트 전체가 Green이다.
- 운영 반영(모델 서버만 재시작) 뒤 다음 날 06:41 점검에서 모델 서버 메모리가 재시작 직후 수준(약 4GB)에 머물고 스왑이 다시 차지 않는다.
- 실제 모델 검증(models·e2e_live)은 필수가 아니다. 리랭크 지연이 걱정되면 사용자 승인 후 models 스모크로 확인한다.
